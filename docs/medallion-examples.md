# Worked Examples — one story traced through Bronze → Silver → Gold

Companion to `docs/medallion-tables.md`. Same table list, but with **real rows taken
from the built pipeline**, so you can see what the data literally looks like at each
layer and how a dollar gets from the invoice to a person.

Everything below follows one cast of characters:

| Who / what | Detail |
|---|---|
| **checkout-service** | service principal (non-human), client id `0999cfae…`, BU Retail, CC-1000 |
| **APP-CHECKOUT** | the Checkout Assistant app, served by `aoai-checkout-prod` |
| **HR Helpdesk Bot** | Copilot Studio agent, bot id `bdd640fb…`, environment "Contoso Production" |
| **Claims Triage Agent** | Copilot Studio agent, BU Insurance |
| Day | `2026-06-30` (Foundry) and `2026-08-01` (Studio) |

> All values are MOCK, generated by `platform/fabric/gen_bronze_data.py`. The
> **shapes** are the real contracts; reproduce them with
> `python3 platform/data-store/build_store.py --query "..."`.

## SILVER — typed, conformed, identity-resolved, cost-allocated

### 1. Type the bill (`silver_cost_charge`)

```csv
charge_date,platform_key,meter_name,model_key,token_direction,consumed_quantity,consumed_unit,pricing_quantity,pricing_unit,billed_cost_usd,list_cost_usd,application_key,business_unit_key
2026-06-30,Foundry,gpt-4.1 Cached Input Tokens,gpt-4.1,cached,6412.0,Tokens,6.412,1K Tokens,0.002725,0.003206,APP-CHECKOUT,BU-RETAIL
```

`Tags` and `x_SkuDetails` are decoded into keys; `ServiceName` becomes `platform_key`.

### 2. Type and resolve the requests (`silver_gateway_request`)

```csv
usage_date,identity_key,identity_class,application_key,business_unit_key,cost_center_key,model_key,input_tokens,output_tokens,cached_tokens,is_error,latency_ms
2026-06-30,0999cfae…,ServicePrincipal,APP-CHECKOUT,BU-RETAIL,CC-1000,gpt-4.1-mini,2541,322,0,FALSE,221.0722
2026-06-30,unknown,Unattributed,APP-SEARCH,BU-UNALLOC,,gpt-4.1-mini,8134,501,0,FALSE,1841.5
```

Strings became numbers, `"None"` became 0, `BackendId` resolved to an application, and
the caller resolved to an identity — or to `unknown` / `BU-UNALLOC`, on purpose.

### 3. Allocate the billed dollars (`silver_foundry_allocation`)

This is the step that makes the platform worth building. For each
(day × app × model × direction), the **billed** cost is split by each identity's share
of the **billed tokens**:

```csv
usage_date,application_key,model_key,identity_key,input_tokens,output_tokens,cached_tokens,requests,latency_ms,cost_usd
2026-06-30,APP-CHECKOUT,gpt-4.1,0999cfae…,122021,17018,6412,8,3193.12,0.325883
```

Input, output and cached tokens are allocated separately because they are priced
differently. Copilot Studio uses the identical pattern with credits
(`silver_studio_allocation`), splitting the tenant's daily PAYG meter across agents.

**The invariant the build enforces:** allocated cost == billed cost, per platform.

```
Azure OpenAI (token allocation)      billed $   71.6533   allocated $   71.6533   delta $0.000000
Copilot Studio (credit allocation)   billed $  373.9920   allocated $  373.9920   delta $0.000000
```

### 4. Conform every platform onto one grain (`silver_usage_conformed`)

Four platforms, four incompatible billing units, so USD is the only common measure and
`unit_type` stays a dimension. `cost_method` records how each dollar was derived:

| cost_method | Used for | cost_is_estimated |
|---|---|---|
| `focus_token_allocation` | Foundry — billed $ split by token share | FALSE |
| `focus_credit_allocation` | Copilot Studio — billed $ split by credit share | FALSE |
| `provider_billed` | GitHub `netAmount`, M365 credit `costUsd` | FALSE |
| `rate_card` | M365 + GitHub seats (nothing is billed as usage) | **TRUE** |
| `usage_signal` | activity proof, zero cost | FALSE |

## GOLD — the star the report binds to

`fact_ai_usage` — a Foundry row (billed, allocated) and a Copilot Studio row:

```csv
usage_date,platform_key,identity_key,model_key,cost_center_key,unit_type,quantity,input_tokens,output_tokens,cached_tokens,requests,cost_usd,cost_is_estimated,is_error,latency_ms,application_key,environment_key,business_unit_key
2026-06-30,Foundry,0999cfae…,gpt-4.1,CC-1000,token,145451,122021,17018,6412,8,0.325883,FALSE,FALSE,3193.122,APP-CHECKOUT,ENV-PROD,BU-RETAIL
2026-08-01,CopilotStudio,claims-triage-agent,,CC-3000,copilot_credit,441.0,0,0,0,8,3.528,FALSE,FALSE,,APP-STUDIO,ENV-PROD,BU-INSURANCE
```

Note the second row: an **agent** is the identity, credits are the quantity, and the
dollars still came from the invoice. `dim_identity` therefore carries people, service
principals, agents, and one `unknown` row so unallocated spend stays visible instead
of being dropped by a join.

### What the layers bought you

| Question | Bronze | Silver | Gold |
|---|---|---|---|
| What did we spend? | ✅ (per resource/meter) | ✅ | ✅ |
| **Who** spent it? | ❌ cost and identity are in different feeds | ✅ allocated | ✅ |
| Compare GitHub to Foundry? | ❌ different units, different keys | ✅ one grain, USD | ✅ |
| Which seats are idle? | ❌ activity is a date in one feed, cost in another | ✅ `active_day` vs `seat_day` | ✅ |
| Does it tie to the invoice? | — | ✅ asserted | ✅ |
